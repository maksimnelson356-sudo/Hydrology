# AGENTS.md — постоянный контракт проекта HydroSphere

Этот файл действует для всех задач в репозитории `D:\hydrolib`.
Руководство для пользователя программы лежит отдельно в `INSTRUCTION.md`
и `README.md`; настоящий файл регулирует работу с кодом.

Он содержит **постоянные правила**, а не пошаговые процедуры. Пошаговая
финальная проверка описана в skill `release-check`.

## Проект

HydroSphere — инженерное программное обеспечение для гидрологических расчётов,
статистического анализа и принятия расчётных решений.

Ключевые каталоги:

- `core/hydrorash/` — гидрологические расчёты: максимальный и минимальный сток,
  регулирование, подпор, гидрографы паводков;
- `core/stats/` — статистика: кривые обеспеченности, параметры, однородность,
  тренды, длительности стока;
- `core/services/` — сервисы, реестр методик, обработка данных;
- `tests/` — автотесты (pytest);
- `DOCS/` — нормативная база, первоисточники, матрицы соответствия.

Корневые `test_*.py` — регрессионные тесты, они тоже собираются pytest.

Конфигурация: `pyproject.toml` (секции `[tool.pyright]`, `[tool.ruff]`,
`[tool.isort]`, `[tool.black]`). Отдельных `pytest.ini`, `setup.cfg`, `tox.ini`
в проекте нет.

## Ключевой приоритет

При конфликте требований выигрывает более высокий пункт:

1. нормативная корректность;
2. математическая корректность;
3. воспроизводимость;
4. прозрачность расчёта;
5. регрессионное тестирование;
6. минимальность изменений.

## Главный рабочий принцип

Проходить цикл:

```text
AUDIT → VERDICT → PLAN → IMPLEMENT → TEST → REVIEW → FINALIZE
```

Нельзя менять код только потому, что он выглядит подозрительно. Сначала должен
быть **доказан** дефект или **подтверждённое** нормативное расхождение; до
получения вердикта файлы не редактируются.

## Нормативные требования

Всегда чётко разделять три сущности:

- **прямое требование нормативного документа** — что источник предписывает;
- **инженерная интерпретация** — как требование реализовано в проекте;
- **текущее поведение кода** — что фактически делает реализация.

Никогда не выдавать инженерную интерпретацию за нормативное требование.

При любом нормативном изменении указывать документ, пункт и страницу, если
источник доступен в репозитории (`DOCS/NORMATIVE/`, `DOCS/`).

Если источник не задаёт однозначного универсального правила, это обязано быть
сказано явно, а не разрешено предположением. Утверждение, справедливое для
одной методики, не распространяется на остальные без отдельной проверки.

## Scope

- Исправлять только подтверждённую проблему.
- Не делать рефакторинг «заодно».
- Не менять API, соседние алгоритмы или другие нормативные периоды без
  отдельного обоснования.
- Не исправлять неподтверждённые проблемы автоматически — помечать их как
  отложенные и выносить в отдельную задачу.
- Не удалять и не ослаблять существующие тесты.

## Тесты

Каждый исправленный дефект должен иметь regression test.

**Обязательность полного прогона зависит от типа задачи:**

- Задача, изменяющая Python-код, тесты или набор методов, — полный
  `pytest -q` перед финализацией обязателен.
- Задача, не затрагивающая исполняемый код и тесты (документация, `.gitignore`,
  инструкции), — полный `pytest -q` не обязателен; выполняются проверки,
  относящиеся к изменённым файлам.

`git diff --check` обязателен перед финализацией **любого** набора изменений.

`pytest tests/test_readme_test_counters.py -q` запускается, когда задача меняет
тесты или счётчики README. Он охраняет согласованность README с реальным
сбором, а не считает тесты.

## README

Единый инвариант: **счётчики тестов в `README.md` должны соответствовать
фактическому количеству тестов.**

Он действует, когда изменение задачи изменило количество тестов или когда
задача явно включает синхронизацию README. Нельзя оставлять README заведомо
устаревшим после изменения количества тестов.

Допустимы два пути: синхронизация в составе той же задачи, что изменила
тесты, либо отдельная задача на синхронизацию счётчиков. Документная задача,
не меняющая тесты, не обязана запускать pytest только ради проверки README.

## Git safety

Никогда автоматически не использовать `git add .`, `git add -A` и
`git add -u`. Причина — в рабочем дереве присутствуют pre-existing untracked
файлы (нормативные PDF, растровые страницы первоисточников, служебные отчёты),
которые не должны попасть в commit.

Staging выполняется только по явно перечисленным путям файлов текущей задачи.
Pre-existing untracked файлы не включаются в commit ни при каких условиях.

Перед commit diff проверяется целиком, а не по выборке. Формулировки и
последовательность командных проверок описаны в skill `release-check`.

## Специализированные процедуры

Отдельные этапы работы оформлены как skills в `.opencode/skills/`:

- `normative-audit` — сверка реализации с нормативным документом;
- `hydrology-audit` — проверка гидрологической и численной корректности;
- `regression-fix` — минимальное исправление подтверждённого дефекта;
- `release-check` — финальная проверка, staging и подготовка commit/push.

Общие правила настоящего файла обязательны всегда; skills их не отменяют.
