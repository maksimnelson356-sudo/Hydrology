# Архитектура: обзор

## Общая схема
Приложение Hydrolib построено по принципу **многослойной архитектуры** с чётким разделением ответственности:
- **Слой представления**: GUI на PyQt6 (gui/)
- **Слой приложения**: Сервисы, оркестрирующие пользовательские сценарии (core/services/)
- **Слой домена**: Бизнес-логика и модели (core/domain/, core/stats/, core/hydrorash/)
- **Слой инфраструктуры**: Persistencia данных, внешние интеграции (file I/O, сериализация)

## Ключевые архитектурные решения

### 1. Элементы Domain-Driven Design
- Чёткие доменные модели в `core/domain/` (Project, Dataset, Methodology и т.д.)
- Доменные сервисы инкапсулируют бизнес-логику (calculation_service, data_quality_service)
- Репозитории неявно присутствуют в слое сервисов (result_store, project_service)

### 2. Сервис-ориентированная архитектура
- Бизнес-логика разложена на сфокусированные сервисы:
  - `CalculationService`: Оркестрирует гидрологические расчёты
  - `DataQualityService`: Выполняет проверку и оценку качества данных
  - `ScenarioService`: Управляет сценариями расчётов
  - `ProjectService`: Работает с файлами проектов (.hsp)
  - `ValidationService`: Валидирует входные данные и параметры
  - `MethodologyRegistry`: Регистрирует и управляет доступными методиками

### 3. GUI на основе сигналов и слотов
- PyQt6 GUI использует паттерн signal/slot для слабосвязанного взаимодействия
- Долгоиграющие операции делегируются worker-потокам (`gui/workers/`)
- GUI остаётся отзывчивым во время вычислений

### 4. Модульный дизайн методик
- Каждая гидрологическая методика реализована как handler
- Handlers регистрируются в `MethodologyRegistry`
- Единый интерфейс позволяет единообразно вызывать через `CalculationService`

### 5. Архитектура потока данных
1. Пользователь вводит данные через GUI или импортирует Excel-файл
2. Данные проходят валидацию через `DataQualityService`
3. Пользователь выбирает методику через GUI
4. `CalculationService` оркестрирует:
   - Вызывает соответствующий handler из `MethodologyRegistry`
   - Handler использует доменные сервисы (stats, hydrorash) для вычислений
   - Результаты сериализуются и сохраняются через `ProjectService`
5. Результаты отображаются в GUI и/или экспортируются

## Точки входа
- `gui/main_window.py`: Главная точка входа приложения (GUI-режим)
- `tools/run_methodology.py`: Консольная точка входа для пакетной обработки
- `build.py`: Точка входа для сборки/скриптов

## Persistencia данных
- Файлы проектов (.hsp): JSON-формат, хранящий полное состояние проекта
- Внешняя база данных отсутствует; всё состояние в файлах
- Сериализация обрабатывается `core/domain/serialization.py`

## Модель конкурентности
- Главный поток: обработка событий GUI
- Worker-потоки: выгрузка долговыполняемых расчётов (реализации `QThread`)
- Потокобезопасная коммуникация через Qt-сигналы/слоты

## Паттерн обработки ошибок
- Исключения поднимаются вверх для обработки на соответствующем слое
- GUI перехватывает исключения и показывает пользователю дружелюбные диалоги
- Ошибки валидации собираются и presentsуются как списки, а не выбрасываются немедленно

## Архитектура тестирования
- Юнит-тесты в `tests/` на pytest
- Тесты организованы по сервисам/доменным модулям
- Mocking используется для изоляции единиц (где целесообразно)
- Интеграционные тесты для взаимодействия сервисов
