# Стратегия и практики тестирования

## Фреймворк тестирования
- **Фреймворк**: pytest (версия >= 8.0 согласно requirements.txt)
- **Обнаружение тестов**: Автоматическое обнаружение файлов `test_*.py` в директории `tests/`
- **Конфигурация**: Корневой `conftest.py` гарантирует импортируемость корня проекта
- **Выполнение**: `python -m pytest tests -q` для тихого вывода
- **Ожидаемый результат**: 79 прошедших тестов (согласно README.md)

## Организация тестов
- **Структура**: Один файл тестов на сервис/доменный модуль
- **Файлы**:
  - `test_data_quality_service.py` - тесты сервиса качества данных
  - `test_domain_services.py` - тесты доменных сервисов
  - `test_methodology_service.py` - тесты сервиса методик
  - `test_project_service.py` - тесты сервиса проектов
  - `test_result_store.py` - тесты хранилища результатов
  - `conftest.py` -共享 фикстур и конфигурации
- **Устаревшие**: Скрипты `test_*.py` в корне проекта существуют, но не являются частью основного набора тестов (см. DOCS/ROADMAP.md, раздел 7)

## Подход к тестированию
### Фокус на юнит-тестирование
- Сервисы тестируются в изоляции там, где это возможно
- Мокирование используется для устранения внешних зависимостей
- Акцент на бизнес-логике, а не на интеграции
- Математические вычисления тестируются косвенно через интерфейсы сервисов

### Характеристики тестов
- **Атомарные**: Каждый тест проверяет конкретное поведение
- **Описательные**: Чёткие имена тестов, объясняющие, что проверяется
- **Независимые**: Тесты могут выполняться в любом порядке
- **Повторяемые**: Согласованные результаты при одинаковых входных данных
- **Быстрые**: Оптимизированы для быстрой обратной связи во время разработки

## Мокирование и изоляция
- **Внешние зависимости**: Мокируются при целесообразности (ввод/вывод файлов, компоненты GUI)
- **Зависимости сервисов**: Внедряются через конструктор или сеттер-инъекцию
- **База данных/Файловая система**: Абстрагируются или мокируются для избежания медленных операций
- **Тестирование GUI**: Ограничено; акцент на базовой логике, а не на взаимодействии с виджетами

## Управление тестовыми данными
- **Фикстуры**: Определяются в `conftest.py` для многоразового использования
- **Примерные данные**: Маленькие, фокусированные наборы данных для тестирования граничных случаев
- **Параметризованные тесты**: Используются там, где применимо, для тестирования нескольких сценариев
- **Жёстко закодированные значения**: Минимальны; предпочтение отдаётся сгенерированным или фикстурным данным

## Цели по покрытию
- **Слой сервисов**: Высокое покрытие логики оркестрации
- **Функции обработчиков**: Покрытие адаптации данных и валидации
- **Доменные модели**: Покрытие сериализации и валидации
- **Точки интеграции**: Покрытие взаимодействия сервисов
- **Пути ошибок**: Явное тестирование условий ошибок и валидации

## Непрерывная интеграция
- **Локальная разработка**: Тесты запускаются часто во время разработки
- **Пре-Коммит**: Подразумевается практика запуска тестов перед коммитом
- **CI/CD**: Неявно настроен в видимых файлах, но тестирование подчёркивается

## Специальные аспекты тестирования
### Тестирование научных вычислений
- **Сравнение с приближением**: Использование приближённого равенства для результатов с плавающей точкой
- **Опорные значения**: Сравнение с известными хорошими значениями или доверенными реализациями
- **Граничное тестирование**: Тестирование граничных случаев (пустые наборы данных, одиночные значения и т.д.)
- **Статистические свойства**: Валидация математических свойств где применимо

### Ограничения тестирования GUI
- **Текущее состояние**: Ограниченное автоматизированное тестирование GUI наблюдается
- **Фокус**: Бизнес-логика тестируется через интерфейсы сервисов
- **Ручная верификация**: Функциональность GUI проверяется вручную
- **Будущая возможность**: Потенциал для использования Qt-специфичных инструментов тестирования (QtTest, pytest-qt)

## Примеры тестов (вывод из структуры)
Хотя конкретное содержание тестов не изучалось, на основе структуры проекта и культуры тестирования:

### Тесты сервисов, вероятно, включают:
- Инициализацию и конфигурацию сервиса
- Регистрацию и поиск методик
- Валидацию входных данных и обработку ошибок
- Успешные пути выполнения
- Распространение и обработку ошибок
- Асинхронное поведение
- Обработку обратных вызовов

### Тесты домена, вероятно, включают:
- Создание и валидацию моделей
- Корректность сериализации/десериализации
- Точность преобразования данных
- Обработку граничных случаев
- Неизменяемость где ожидается

## Критические точки качества
- **Перед слиянием**: Тесты должны проходить перед интеграцией кода
- **Отслеживание покрытия**: Подразумевается акцент на поддержании/увеличении покрытия
- **Профилактика регрессий**: Набор тестов растёт вместе с функциями, чтобы предотвратить регрессии
- **Документация**: Тесты служат исполнимой документацией для ожидаемого поведения

## Инструменты и утилиты, поддерживающие тестирование
- **conftest.py**: Централизованная конфигурация тестов и фикстуры
- **test_* файлы**: Организованы по подсистемам для лёгкого нахождения
- **pytest**: Богатая библиотека утверждений и экосистема плагинов
- **Контроль версий**: Тестовый код обрабатывается наравне с продуктовым кодом

## Пробелы и возможности
- **Тестирование GUI**: Ограниченное покрытие автоматизированными тестами GUI наблюдается
- **End-to-End Тестирование**: Мало тестов пользовательских сценариев видно
- **Тестирование производительности**: Нет явного набора тестов производительности
- **Свойство-ориентированное тестирование**: Возможность использования библиотек типа hypothesis
- **Мутационное тестирование**: Возможность оценки эффективности тестов

## Наблюдаемые лучшие практики
- **Чёткое разделение**: Код тестов зеркально отражает структуру продуктового кода
- **Фокус на поведении**: Тесты проверяют, что делает код, а не как
- **Поддерживаемость**: Тесты обновляются вместе с изменениями продуктового кода
- **Изоляция**: Усилие по тестированию единиц в изоляции там, где это выгодно
- **Документация**: Имена тестов и комментарии объясняют намерение
