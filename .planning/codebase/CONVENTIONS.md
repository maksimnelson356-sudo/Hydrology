# Соглашения по оформлению кода и шаблоны

## Язык и стиль
- **Язык**: Python 3.10+
- **Руководство по стилю**: PEP 8 с адаптациями проекта
- **Длина строки**: 100 символов (настроено в pyproject.toml для black, ruff, isort)
- **Отступы**: 4 пробела (стандарт Python)
- **Кавычки**: Двойные кавычки для строк (согласовано во всём кодовой базе)
- **Импорты**:
  - Сначала стандартная библиотека
  - Затем сторонние библиотеки
  - В конце импорты самого приложения
  - Внутри каждой группы — алфавитный порядок

## Соглашения об именовании
- **Модули**: snake_case (например, `data_quality_service.py`)
- **Классы**: PascalCase (например, `CalculationService`, `Project`)
- **Методы/Переменные**: snake_case (например, `calculate_statistics`, `data_loader`)
- **Константы**: UPPER_SNAKE_CASE (например, `DEFAULT_PRECISION`, `ALPHA_THRESHOLD`)
- **Параметры**: snake_case (совпадает с именованием переменных)
- **Исключения**: PascalCase, оканчивающиеся на "Error" (например, `CalculationError`)

## Стиль документации
- **Строки документации модуля**: В начале каждого файла, описывающие назначение
- **Строки документации класса**: Для всех публичных классов
- **Строки документации метода**: Для всех публичных и защищённых методов
- **Формат**: Смешанное использование Google-styl и NumPy-styl docstrings
- **Комментарии**: Используются экономно, в основном для объяснения сложной логики
- **Не английский**: Русский язык используется в комментариях и документации (согласуется с происхождением проекта)

## Паттерны организации кода

### 1. Паттерн слоя сервисов
- Сервисы расположены в `core/services/`
- Тонкий слой оркестрации, делегирующий работу доменным модулям
- Сервисы регистрируют обработчики через паттерн реестра
- Сервисы обрабатывают сквозные аспекты (валидация, обработка ошибок, метаданные)

### 2. Паттерн обработчика/стратегии
- Каждая методика реализована как функция-обработчик
- Обработчики регистрируются в словаре `HANDLERS`
- Единый интерфейс: `func(CalculationContext) -> dict[str, Any]`
- Обработчики делегируют работу существующим доменным модулям, не выполняя математику сами
- Сосредоточены на адаптации данных и сериализации (numpy/pandas → обычные типы Python)

### 3. Объекты передачи данных (DTO)
- Использование `@dataclass` для простых контейнеров данных (например, `CalculationContext`)
- Неизменяемые модели данных, где целесообразно
- Чёткое разделение между доменными моделями и контекстами сервисов

### 4. Обработка ошибок
- Пользовательские типы исключений (`CalculationError`) для ошибок, специфичных для домена
- Исключения включают контекстную информацию (название методики, исходная ошибка)
- Ошибки валидации собираются и отчитываются в виде списков, а не приводят к немедленному исключению
- Слой GUI перехватывает исключения и выдаёт дружелюбные сообщения пользователю

### 5. Паттерны сериализации/очистки
- Специальные функции очистки для преобразования типов numpy/pandas в обычные типы Python
- Функции-помощники: `_clean_scalar()`, `_clean()`, `_to_float_dict()`
- Обеспечивает пригодность для JSON-сериализации для хранения в файлах .hsp
- Согласованный шаблон используется во всех обработчиках

### 6. Внедрение зависимостей
- Паттерн контейнера сервисов в `bootstrap.py`
- Сервисы создаются и соединяются вместе при запуске приложения
- Слабая связность между компонентами
- Легко мокировать для тестирования

### 7. Модель потоков
- GUI остаётся отзывчивым благодаря worker-потокам (`QThread`)
- Долгие вычисления вынесены в фоновые потоки
- Коммуникация через сигналы/слоты Qt
- Простая асинхронная реализация в `CalculationService.execute_async()`

## Соглашения по тестированию
- **Фреймворк**: pytest
- **Именование файлов**: `test_<module_name>.py`
- **Организация тестов**: Один файл тестов на сервис/модуль
- **Фикстуры**: Определяются в `conftest.py` для общего использования в тестах
- **Мокирование**: Используется для изоляции единиц от внешних зависимостей
- **Утверждения**: Чёткие и описательные
- **Покрытие**: Стремимся к высокому покрытию логики сервисов

## Управление конфигурацией
- **Конфигурация инструментов**: Централизована в `pyproject.toml`
  - pyright: конфигурация проверки типов
  - ruff: правила линтинга
  - black: форматирование кода
  - isort: сортировка импортов
- **Зависимости**: Перечислены в `requirements.txt` с ограничениями версий
- **Окружение**: Нет жёстко закодированных путей; используются относительные пути или настройки

## Практики работы с Git и репозиторием
- **Файл игнорирования**: Всеобъемлющий `.gitignore`, исключающий кэши, байт-код, файлы IDE
- **Коммиты**: Атомарные, сфокусированные, с описательными сообщениями
- **Ветви**: Подразумевается модель ветвления по функциям
- **Теги**: Используются для меток версий (видно по `version.py`)

## Значимые антипаттерны, которых удалось избежать
- **Бог-объекты**: Нет одного класса/модуля с чрезмерными обязанностями
- **Жёсткая связность**: Сервисы взаимодействуют через чётко определённые интерфейсы
- **Примитивная одержимость**: Использование доменно-специфичных объектов вместо примитивных типов
- **Магические числа**: Константы определены и именованы соответствующим образом
- **Глубокое вложение**: Приемлемый уровень вложения; ранние возвраты используются для снижения сложности

## Интернационализация/Локализация
- **Язык интерфейса**: Русский (согласован с пользовательской базой и документацией)
- **Комментарии в коде**: Смешанный русский/английский (больше русского в недавнем коде)
- **Строковые литералы**: Строки, обращающиеся к пользователю, на русском
- **Технические термины**: Английский используется для технических концепций и названий методик

## Принципы организации файлов
- **Разделение ответственности**: Чёткое деление между core, gui, tests, tools, docs
- **Связность**: Связанная функциональность группируется вместе (например, всё статистическое в `core/stats/`)
- **Обнаруживаемость**: Логичное размещение файлов облегчает поиск функциональности
- **Масштабируемость**: Структура допускает добавление новых методик/сервисов без разрушения существующего
