# regression-fix

Превращение **подтверждённого** дефекта в минимальное безопасное изменение кода
с регрессионным покрытием и полной проверкой.

## Цикл

```text
CONFIRMED DEFECT → MINIMAL PATCH → REGRESSION TEST → TARGETED TESTS
→ FULL TESTS → DIFF REVIEW
```

Каждый шаг имеет вход. Переходить к следующему без выполнения предыдущего
нельзя.

## Правила

### До подтверждения дефекта код не менять

Вход цикла — подтверждённый дефект. Если дефект не доказан, сначала
`normative-audit` или `hydrology-audit`. Сомнение в коде не является
основанием для правки.

### Минимальный patch

- менять только то, что доказанно неверно;
- не переименовывать без необходимости;
- не переформатировать соседние строки;
- не трогать соседние алгоритмы и другие нормативные периоды.

### Публичный API сохраняется

Сигнатуры, имена параметров, значения по умолчанию, формат возврата и
ключи словарей остаются прежними, если задача не требует смены контракта
явным решением.

### Assertions не ослабляются

- не удалять тесты;
- не заменять `assert` на предупреждение;
- не ослаблять сравнение (`allclose` с увеличенной точностью, `>=` на `>`),
  чтобы тест начал проходить;
- не выносить ожидаемое значение в константу, которую правится вместе с кодом.

### Добавить regression test

Тест обязан **падать на старом коде** и **проходить на новом**. Проверить это
явно, а не предполагать: собрать старую реализацию в памяти или временно
вернуть константу, прогнать тест, зафиксировать оба результата, восстановить.

Тест должен фиксировать **нормативное поведение**, а не механически
следовать за изменённой константой.

Дополнительно добавлять boundary или negative case, если это релевантно:
граница сезона, крайний элемент, пустой вход, значение на границе таблицы.

### Не смешивать независимые исправления

Одно изменение — одна причина. Если в процессе найден другой дефект, он
помечается `DEFERRED` и выносится в отдельную задачу. Смешивание делает
невозможным установить, какое изменение вызвало регрессию.

## Проверки

```powershell
# Targeted — сразу после патча
pytest tests/<файл_регрессии>.py -q

# Перед финализацией — обязательно
pytest tests/test_readme_test_counters.py -q
pytest -q
git diff --check
```

### README counters

**Инвариант:** счётчики тестов в `README.md` должны соответствовать фактическому
количеству тестов.

Инвариант действует, когда изменение задачи изменило количество тестов или
когда задача явно включает синхронизацию README. Проверку выполняет
`tests/test_readme_test_counters.py` — он сравнивает числа вида `N passed` в
README с `pytest --collect-only`.

Допустимы два пути:

- синхронизация в составе той же задачи, что изменила тесты;
- отдельная задача только на синхронизацию счётчиков.

Оба допустимы; выбирается тот, который не смешивает исправление кода с
правкой документации без необходимости. Недопустимо третье: оставить README
заведомо устаревшим после изменения количества тестов.

Если счётчики рассинхронизированы, но задача тесты не меняла, это
предсуществующее расхождение — оно фиксируется в отчёте отдельной задачей,
а не правится молча в рамках текущей.

### Diff review

```powershell
git diff --check
git diff --stat
git diff -- <файлы_задачи>
```

Проверить, что diff содержит **только** ожидаемые файлы и ожидаемые строки.
Если в diff попал файл, не относящийся к задаче, — это ошибка задачи, а не
допустимое «заодно».

## Формат отчёта

1. Какие production-строки изменены.
2. Какие тесты изменены или добавлены.
3. Результаты всех проверок.
4. Новое количество тестов.
5. Подтверждение, что незатронутое осталось нетронутым.
6. `DEFERRED` — что найдено, но не исправлено.

```text
## DEFERRED

- <проблема> — <доказательство>, <файл:строка>
```

Если таких проблем нет:

```text
## DEFERRED

None.
```
