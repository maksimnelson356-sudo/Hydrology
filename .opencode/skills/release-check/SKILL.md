# release-check

Финальная проверка перед commit и push.

**Границы воздействия:**

```text
working tree:    не изменяется автоматически
file contents:   не изменяются
index / staging: может изменяться только явно перечисленными путями,
                 и только если staging выполняется как часть процедуры
```

Процедура не создаёт commit и не выполняет push без отдельного разрешения
владельца.

## 1. Проверка состояния

```powershell
git status --short
```

Ожидается: изменены только файлы текущей задачи плюс явно известные
pre-existing untracked файлы. Любой неожиданный файл — остановиться и
выяснить происхождение до продолжения.

## 2. Проверка diff

```powershell
git diff --check
git diff --stat
git diff
```

- `git diff --check` обязан быть пустым. Любой вывод означает проблему
  пробельных ошибок или конфликтных маркеров.
- `git diff` читается целиком, а не по выборке. Проверяется, что каждая
  правка относится к задаче.
- Правки документации, добавление тестов и изменение production-кода должны
  быть обоснованы отдельно; смешивание без необходимости — нарушение scope.

## 3. Тесты

```powershell
pytest tests/test_readme_test_counters.py -q
pytest -q
```

Полный `pytest -q` обязателен, если задача изменяла исполняемый код, тесты или
набор методов: он собирает и `tests/`, и корневые `test_*.py`. Для задач,
не затрагивающих исполняемый код и тесты, полный прогон не обязателен.

`tests/test_readme_test_counters.py` запускается, когда задача меняет тесты или
счётчики README.

### README counters

**Инвариант:** счётчики тестов в `README.md` должны соответствовать фактическому
количеству тестов.

Инвариант действует, когда изменение задачи изменило количество тестов или
когда задача явно включает синхронизацию README. Синхронизация выполняется
либо в составе той же задачи, что изменила тесты, либо отдельной задачей.
Недопустимо оставить README заведомо устаревшим после изменения количества
тестов.

Падение `test_readme_test_counters.py` при задаче, не меняющей тесты, означает
предсуществующее расхождение: оно фиксируется в отчёте отдельной задачей, а не
правится молча в рамках текущей.

## 4. Staging safety

Никогда не использовать:

```powershell
git add .
git add -A
git add -u
```

Добавлять только конкретные файлы текущей задачи, перечисленные поимённо:

```powershell
git add <путь1> <путь2>
```

Причина: в репозитории присутствуют pre-existing untracked файлы
(нормативные PDF, растровые страницы первоисточников, служебные отчёты).
`git add .` захватит их и включит в commit.

## 5. Проверка перед commit

```powershell
git diff --cached --check
git diff --cached --stat
git diff --cached
```

`git diff --cached` читается целиком. Проверяется, что в индекс попали
только файлы задачи и ни один pre-existing untracked файл.

## 6. Проверка после commit

```powershell
git show --stat --oneline --decorate HEAD
git status --short
```

Проверяется **не количество строк**, а соответствие ожидаемому состоянию:

```text
ожидаемое:  файлы задачи исчезли из status — они теперь tracked и закоммичены
ожидаемое:  pre-existing untracked файлы остались ровно те же
ошибка:      файл задачи всё ещё значится как untracked или modified —
             он не попал в commit
ошибка:      pre-existing untracked файл исчез из списка —
             он был ошибочно включён в commit
сигнал:     появились неожиданные новые файлы — исследовать происхождение
```

Ошибка первого вида опаснее: она незаметна, потому что `git status` выглядит
«грязным» и это легко списать на ожидаемый мусор.

Если commit-hook отклонил commit — исправить причину и создать **новый**
commit; amend не применять.

## 7. Push

Push выполняется **только** после успешной проверки commit из шага 6 и только
по явному требованию задачи. Не использовать `--force` без отдельного
обоснования.

## Формат отчёта

- состояние рабочего дерева;
- результат `git diff --check`;
- результат targeted и полного прогонов;
- количество тестов;
- список файлов, попавших в индекс;
- подтверждение, что pre-existing untracked файлы не включены;
- что осталось незавершённым, если что-то осталось.
